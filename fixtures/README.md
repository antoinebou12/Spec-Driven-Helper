# Fixtures

Two reference projects, each as a `.plan/` Markdown folder and as a zip. Both are generated by `scripts/generate-fixtures.ts` and must not be edited by hand.

| Fixture | What it is |
| --- | --- |
| `default-project/.plan/` and `default-project.plan.zip` | The complete example project (Customer Request Portal): every module answered, requirements, decisions and tests linked, and a board with cards in every column. |
| `sdd-studio/.plan/` and `sdd-studio.plan.zip` | This repository: its stack, CI, containers and contracts, detected by the same import rules a user runs on a repository, plus its real board from `.plan/tasks.md` and `.plan/backlog.md`. |

## Use them

- **In the app:** open **Publish & handoff → .plan folder → Import a .plan zip** (or pick a folder), review the preview, then import.
  - The specification arrives as a proposal to accept in **Proposals**.
  - The cards go straight to the board.
- **Through the API:** send `POST /api/v1/projects/{id}/plan-folder/import` with `{ files: { path: content }, preview: true }`. Then send `preview: false` with the `expectedBoardRevision` from the preview.
- **In a repository:** copy a `.plan/` folder next to your code. Coding agents read `.plan/README.md`, `spec/` and `tasks.md`.

## Keep them current

```bash
pnpm fixtures
```

Run it after changing `.plan/`, the exporters or the example project. `pnpm fixtures:check` (CI) fails when they are out of date. `tests/fixtures.test.ts` also checks four things:

- the folder and the zip match;
- the specification is a valid bundle;
- both fixtures import through the API;
- accepting the imported default project reproduces the example's answers exactly.
