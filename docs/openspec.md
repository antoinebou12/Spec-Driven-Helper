# OpenSpec exchange

SDD Studio exchanges files with OpenSpec; its canonical specification, proposals and board remain authoritative inside the app. There is no second task database, automatic synchronization or uploaded-command execution. Spec Kit and `.plan` exports are unchanged.

## Export

In **Publish & handoff**, choose **OpenSpec** in the grouped export selector. Diagnostics appear before Download. A bundle with missing scenarios, missing normative statements or other unsupported content is labeled **Draft**. Even a complete snapshot is never labeled CLI-validated by the app.

The ZIP contains `openspec/specs/<module>/spec.md`, `openspec/config.yaml`, a version-1 `openspec/sdd-manifest.json`, diagnostics, and root `spec.md`, `PRODUCT.md`, `DESIGN.md` and `tasks.md`. Requirements retain their item IDs and recorded acceptance scenarios. Module assignment uses explicit item-ID mentions in recorded section Markdown or answers, in canonical module order; unmatched items belong to `scope`. Missing scenarios are not generated. Tasks are a handoff, not an invented active change. Baseline exports omit the live board, and disabled board features omit tasks.

## Import and review

Open **Overview > Import existing work > OpenSpec**, then choose a folder or ZIP. Use the repository folder containing `openspec/`, not an unlabelled set of capability files. Multiple active changes require selecting one; archives are ignored. A snapshot imports the supplied requirements, never deleting missing files or items.

Preview is read-only. Inspect diagnostics, the proposed specification patch, source documents and the separate Tasks disclosure. **Propose** creates a reviewable proposal, not a specification write. **Import tasks** independently confirms the board merge using the preview's board revision. Existing dependencies, assignees and PR links survive omissions in the checklist. A checked task is task progress, never baseline approval.

ADDED, MODIFIED, REMOVED and RENAMED requirements are supported. Removals require Reason and Migration. IDs and manifest mappings are checked; ambiguous names, conflicting identities and malformed deltas block confirmation. Proposal/design prose remains untrusted source material visible in the proposal. Imported review or verification claims do not grant approval.

Limits: 400 files, 2 MB per decoded file, 12 MB total UTF-8 content. ZIP expansion is bounded while reading. Traversal, absolute paths, duplicate normalized paths and secret-looking files are rejected. Uploads never run a CLI, AI call, Git write or archive action.

## API and access

| Route | Access and behavior |
| --- | --- |
| `GET /api/v1/projects/:id/openspec` | Read permission; diagnostics, source revision, draft status; no writes |
| `GET /api/v1/projects/:id/export/openspec?expectedRevision=N` | Read permission; ZIP, with a stale-revision conflict if supplied |
| `POST /api/v1/projects/:id/openspec/import` | Edit permission; preview by default |

The import body contains `files` (path-to-text mapping), `baseRevision` and optional `selectedChange`. Confirmation adds `preview: false` and `action: "specification"` or `"board"`; board confirmation also requires `expectedBoardRevision`. Responses contain diagnostics, proposed changes and the resulting proposal ID when applicable. Stale revisions return 409. Specification imports are idempotent for the same project revision, patch and sources.

All routes require the OpenSpec feature; imports additionally require Import, and confirmed board merges require Board. Disabled features return 403. Server-side project permissions apply regardless of visible controls. Confirmations and exports are audited. See the running application's `/api/docs` for the route reference.

## Repository workflow

Use the pinned development CLI with `pnpm exec openspec`; do not install it globally. Codex, Claude Code and GitHub Copilot integrations are generated by version **1.14.1**. Maintenance instructions and skills remain separate. Read `PRODUCT.md`, `DESIGN.md`, `AGENTS.md` and `.plan` before a new change.

Only new repository changes use `openspec/changes/`. Existing unfinished work stays in `.plan`. Every OpenSpec task checkbox references one `TASK-###`; `.plan/tasks.md` owns verified completion. Partially verified tasks stay unchecked in OpenSpec. `pnpm openspec:check` rejects task-status drift and runs strict structural validation. Regenerate task intent/spec documents with `pnpm plan:tasks`.

The core profile does not guarantee an installed verify workflow. Structural CLI validation is not implementation verification: run repository typecheck, lint, affected tests and UI accessibility/browser checks, then obtain explicit review before archiving. Never archive automatically. Production Docker images exclude the repository CLI.

## En francais

Dans **Publication et transmission**, choisissez **OpenSpec** puis consultez les diagnostics avant **Telecharger**. Un export incomplet reste un **Brouillon**; aucun scenario n'est invente.

Dans **Vue d'ensemble > Importer un travail existant > OpenSpec**, choisissez un dossier ou ZIP. Selectionnez explicitement un changement si plusieurs sont presents.
